# Architecture Decision Record

| ADR | Date | Status | Context | Decision | Alternatives considered | Consequences |
|---|---|---|---|---|---|---|
| [1] | 2026-10-09 | Decided | The application needs a simple backend that can run in one container and store data locally. | Use Flask because it is lightweight and easy to use. Use SQLite because it is required for the project and does not need a separate database service. | Django was rejected because it would add more complexity than this small application needs. | The application will be simple to run and maintain, with the backend and database in one container. |
| [2] | 2026-10-12 | Decided | The application needs two meaningful feature domains instead of only basic habit CRUD. | Keep habit management responsible for creating, listing, and deleting habits. Keep completion tracking responsible for daily completion history and streak calculations, using the habit ID to connect the two domains. | Keeping all behavior in one module was rejected because the domains would be harder to separate in a future service-based design. | Each domain has a clear responsibility and can be tested independently while still running in the same application for Assignment 1. |
| [3] | 2026-10-12 | Decided | Both feature domains need persistent data, while a completion belongs to one habit. | Store habits in a `habits` table and daily records in a `completions` table linked by `habit_id`. Enforce one completion per habit and date with a unique constraint, and delete completions when their habit is deleted. | Storing completions as a list inside each habit was rejected because separate rows are easier to query and test. | SQLite enforces the relationship and prevents duplicate daily records. The schema can later be separated along the same domain boundary. |
| [4] | 2026-10-12 | Decided | The assignment requires automated tests and at least 70% coverage of the two domains' core logic. | Use pytest with pytest-cov and test habit CRUD, completion rules, streaks, persistence, and cascade deletion using temporary SQLite databases. Keep framework-only details thinner than business behavior. | Manual testing was rejected because it would not provide repeatable checks or a coverage measurement. | The current suite provides repeatable checks and reached 98% coverage for `app.py`, while keeping the tests understandable for the comprehension check. |
| [5] | 2026-11-11 | Decided | Assignment 2 requires every service image to be built on pushes and pull requests, while images must only be published after a successful change reaches `main`. | Use a GitHub Actions matrix job with one matrix entry for each service. Build the `habits` and `completions` Dockerfiles on every push and pull request. Log in to GHCR and push images only for a push to `main`, tagging each image with the commit SHA. Pull requests and other branch pushes build images without publishing them. | Separate duplicated jobs were rejected because the matrix keeps the two service build paths consistent. Publishing on pull requests was rejected because it could expose unreviewed images and does not satisfy the requirement that publishing happens on `main`. | Dockerfile errors are detected before merge, and each merged `main` commit can be identified in GHCR by its immutable commit-SHA image tags. Azure deployment and post-deployment health checks remain separate decisions for the later CD phase. |
| [6] | 2026-11-21 | Decided | The assignment requires the two feature domains to become separate services with a server-side cross-seam flow. ADR-2's domain boundary remains valid. | Split the application into `services/habits` and `services/completions`. Habits owns habit lifecycle data and completions owns completion history and streak data. The completions service verifies a habit through `HABITS_URL` before recording a completion. | Having the browser call both services directly was rejected because at least one flow must cross the seam server-side. Moving the seam was unnecessary because habit ownership and completion tracking remain distinct and loosely coupled. | A completion cannot be recorded for an unknown habit. Cross-service calls use `HABITS_TIMEOUT_S`, missing habits produce `404`, and an unavailable habits service produces `503`. The two services do not share an in-process database or module. |
| [7] | 2026-11-21 | Decided | Assignment 2 requires SQL Server databases owned separately by each service and versioned in-place migrations. | Use numbered SQL migration files applied automatically and in order at startup, with applied migrations recorded in a `schema_migrations` table. Each service will own and connect only to its own SQL Server database. A plain `habit_id` will replace the old cross-table foreign key. | Rebuilding or dropping tables on restart was rejected because it loses user data. Untyped migration state in application startup was rejected because it cannot prove exactly-once application across boots. | Cross-domain referential integrity will be enforced by the completions service's habits HTTP call. Recovery for a bad migration will be forward-only: stop deploys, restore the database when available, or add a corrected migration rather than editing an applied migration. |
| [8] | 2026-11-21 | Decided | The application must run on pay-per-use Azure infrastructure while tolerating scale-to-zero and SQL Server cold starts. | Deploy two Flask services to separate Azure Container Apps on the Consumption plan, with minimum replicas zero and maximum replicas one. Use one serverless Azure SQL Database per service on the shared logical server, one Static Web App for the UI, and GHCR for images. | Fixed-cost or always-on alternatives such as ACR, dedicated Container Apps workload profiles, App Service, and VMs were rejected to match the cost and scaling contract. | Container and SQL cold starts will require startup/retry logic and bounded health-check waiting. Migrations must run with one replica to prevent concurrent startup migration attempts. |
| [9] | 2026-11-21 | Decided | Assignment 2 requires reliable CI gates and a full CD path, while Azure SQL must not be contacted by CI. | CI will install dependencies, lint and test each service, run cross-seam integration coverage, validate OpenAPI and `system.yaml`, measure at least 70% service core coverage, and build both images on every push and pull request. CD on `main` will publish SHA-tagged images, deploy Azure resources and the UI, and check deployed health endpoints. | Testing against Azure SQL was rejected because it could wake billed database capacity. A final merge without CI was rejected because it bypasses the required image, test, and contract gates. | CI provides repeatable pre-merge evidence and deploys only from a passed `main` commit. Load, Azure failure recovery, and UI visual rendering will remain outside this implementation's primary automated gates unless specifically added later. |
| [10] | 2026-11-21 | Decided | Assignment scope excludes service meshes, message brokers, background workers, Kubernetes, additional databases, and another frontend/gateway container. | Deliberately do not build a service mesh or message broker. Keep synchronous HTTP between the two services and use the static UI with direct HTTPS calls. | Caches, queues, Kafka-style event processing, Kubernetes, and a gateway were rejected because they add infrastructure and cost without an Assignment 2 requirement. | The system will tolerate the second service being unavailable through timeout and clear degradation rather than asynchronous resilience infrastructure. A queue or gateway would become worthwhile if throughput, independent retries, fan-out, or routing complexity grew substantially. |
